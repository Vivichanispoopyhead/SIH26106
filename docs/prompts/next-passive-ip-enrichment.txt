NEXT FEATURE

Implement the first safe passive-enrichment vertical slice for extracted IP
addresses.

Goal:
For every public IP observed in the parsed email's Received chain or
indicators, produce optional provider-independent enrichment while preserving
forensic provenance and graceful failure behavior.

SCOPE

1. Add an enrichment domain model.

Define typed structures for:
- Enrichment status
- IP address
- Country/region/city when available
- Latitude/longitude when available
- ASN
- ISP or organization
- Provider
- Provider confidence
- Retrieved timestamp
- Provenance
- Failure code and safe user-facing message

Every enrichment result must clearly be marked as:
- ENRICHED when returned by a provider
- NOT_APPLICABLE for private, loopback, multicast, documentation and reserved
  IPs
- FAILED when a provider was attempted but failed
- NOT_CONFIGURED when no provider is configured

2. Add a provider-neutral interface.

Use an interface similar to:

type IPEnricher interface {
    Lookup(context.Context, string) (domain.IPEnrichment, error)
}

The core pipeline must not depend directly on one external vendor.

Add an unavailable/no-op implementation that returns explicit not_configured
results instead of pretending that no threat exists.

3. Implement one safe provider adapter.

Prefer an environment-configured provider with:
- API key read only from environment
- Configurable endpoint
- Request timeout
- Maximum response size
- No API key in logs, errors, tests or reports
- Context cancellation
- HTTP status validation
- Strict response decoding
- No retries that could unexpectedly multiply provider traffic

If a local MaxMind database is already available, support it behind the same
interface. Do not require a large database download for tests.

Use a local HTTP test server for provider tests. Tests must not call a real
external provider.

4. Add IP classification before provider calls.

Do not send these addresses to an external provider:
- Loopback
- Private RFC1918/RFC4193 ranges
- Link-local addresses
- Multicast addresses
- Documentation/test ranges
- Unspecified addresses
- Invalid IP values

Return a structured not_applicable result for these cases.

5. Integrate enrichment into StartAnalysis.

Sequence:

Parse
  -> authentication and Received-chain analysis
  -> indicator extraction
  -> passive IP enrichment
  -> AI analysis
  -> deterministic risk evaluation
  -> persistence

The implementation may remain synchronous for this MVP, but preserve explicit
partial status behavior.

Rules:
- Enrichment failure must not erase parsed, authentication or AI results.
- AI failure must not erase enrichment.
- If one IP fails, other IPs may still succeed.
- Results identify the source IP and provider.
- Missing enrichment must not become a negative reputation.

6. Extend the canonical analysis response.

Update docs/api_contract.md before implementing the response shape.

Add a stable field such as:

    "ip_address": "203.0.113.10",
    "status": "not_applicable",
    "provenance": "ENRICHED",
    "country": null,
    "region": null,
    "city": null,
    "latitude": null,
    "longitude": null,
    "asn": null,
    "organization": null,
    "provider": null,
    "confidence": null,
    "retrieved_at": null,
    "failure": null
  }
]

Choose the final exact shape based on existing conventions and document:
- statuses
- nullable fields
- provenance values
- failure behavior
- geolocation disclaimer

Do not break existing frontend consumers. Existing fields remain
backward-compatible.

7. Add enrichment-aware risk signals carefully.

Do not assign maliciousness solely from country, city, ASN or ISP.

Only add safe deterministic signals such as:
- public IP observed
- enrichment unavailable
- private IP observed
- a provider-reported reputation signal, if the provider actually supplies it

Geolocation is not proof of identity or maliciousness.

Keep distinctions:
- OBSERVED: IP was present in the email
- ENRICHED: provider returned metadata
- INFERRED: backend derived a conclusion
- AI-ASSESSED: model output

Persist enrichment with the canonical analysis result or a separate normalized

The result must survive:
- PostgreSQL save and reload
- MemoryStore save and reload
- partial provider failure

Do not add Redis yet. Redis caching is a later task after the provider contract

NEXT FEATURE

Define the threat-intelligence behavior and evaluation contract for safe
passive IP enrichment.

This task is not URL crawling, active scanning, autonomous agent behavior or
attachment analysis.

GOALS

- Interpret enrichment results conservatively.
- Ensure provider data never becomes unsupported attribution.
- Ensure enriched data improves investigation context without overriding
  observed forensic evidence.
- Keep enrichment confidence and AI confidence separate.

REQUIREMENTS

1. Define the enrichment interpretation contract.

Document interpretation of:
- Country
- Region
- City
- Latitude and longitude
- ASN
- ISP/organization
- Hosting provider
- Provider confidence
- Provider timestamp
- Missing provider data

Explicitly state:
- Geolocation is an IP-derived estimate.
- It does not identify a person.
- It does not prove the sender's physical location.
- It does not prove maliciousness.
- A hosting provider or cloud ASN is not automatically malicious.
- A public IP is not automatically suspicious.

2. Define safe enrichment statuses.

Use or review:
- enriched
- not_applicable
- not_configured
- failed
- partial

Explain the difference between:
- provider did not run
- provider ran and found no data
- provider failed
- address is not eligible for lookup

Never map any of these automatically to benign.

3. Review AI-to-enrichment interaction.

Gemini should receive normalized enrichment metadata only if the backend
explicitly includes it in the AI input contract.

If enrichment is sent to Gemini:
- Label it ENRICHED.
- Include provider and retrieval time.
- Do not treat geolocation as identity.
- Do not infer nationality, physical location or intent from geolocation.
- Do not claim country or ASN proves maliciousness.
- Do not invent provider facts.

If enrichment is not yet included in AI input, document that the risk engine
uses it separately and do not expand the Gemini prompt unnecessarily.

4. Define reputation interpretation rules.

If the provider supplies reputation:
- Accept only documented provider fields.
- Distinguish provider observation from platform inference.
- Do not convert unknown reputation into clean.
- Do not convert unavailable provider status into malicious.
- Do not let one weak field produce a high-confidence verdict.
- Preserve provider name, timestamp and safe evidence metadata without storing
  unsafe full responses.

5. Review risk-engine mapping.

Recommend bounded, explainable signals such as:
- enrichment available
- enrichment unavailable
- provider-reported abuse signal
- provider confidence below a configured threshold

Do not add points for:
- country alone
- city alone
- ISP name alone
- cloud hosting alone
- public IP alone

Every new risk signal must:
- Have a stable code.
- Have a clear description.
- State provenance as ENRICHED or INFERRED.
- Include an evidence reference.
- Have deterministic tests.
- Not override executable attachment or authentication evidence.

6. Build a local evaluation matrix.

Create table-driven cases for:
- Private IP
- Documentation IP
- Ordinary public business relay
- Public cloud relay with no abuse signal
- Provider reports suspicious reputation
- Provider returns no reputation
- Provider timeout
- Provider returns conflicting or incomplete metadata
- AI classifies phishing while enrichment is neutral
- AI returns unknown while enrichment reports abuse
- Failed authentication with neutral enrichment
- Passed authentication with suspicious provider reputation

For every case define:
- Expected enrichment status
- Expected provenance
- Allowed risk signal
- Forbidden conclusion
- Expected confidence behavior
- Whether final analysis is completed or partial

7. Prompt and model policy review.

Update the Gemini system instruction only if needed. If enrichment is added
to AI input, explicitly instruct Gemini:
- Enriched metadata is not ground truth.
- Geolocation is not identity.
- Provider confidence is not threat confidence.
- Do not infer nationality, physical location or actor attribution.
- Do not invent reputation results.
- Keep evidence references tied to supplied IDs.
- Use unknown when evidence is insufficient.

8. Avoid unsafe expansion.

Do not add:
- URL browsing
- DNS lookups of attacker-controlled domains
- WHOIS/RDAP calls
- Active scanning
- Attachment execution
- Autonomous tool calling
- Agent loops
- Vector search
- Embeddings
- A second LLM provider

9. Update:
- docs/analysis-pipeline.md
- docs/data-model.md
- docs/api_contract.md if AI input or risk semantics change
- A concise enrichment evaluation document only if necessary

10. Validation:

Run existing backend tests and build after any code changes.
