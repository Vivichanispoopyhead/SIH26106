SIH26106 - JUDGE PROJECT BRIEF

============================================================
1. ONE-LINE DESCRIPTION
============================================================

SIH26106 is an AI-powered email threat and forensic intelligence platform.
It accepts an RFC 5322 .eml file, preserves the original artifact, extracts
technical evidence, reconstructs forensic signals, and produces an explainable
AI-assisted threat assessment.

Short judge explanation:

"We turn a suspicious email into a traceable forensic case by preserving the
original artifact, extracting headers and indicators, analyzing authentication
and relay signals, and using Gemini to provide an explainable phishing
assessment with confidence and evidence references."

============================================================
2. PROBLEM
============================================================

Security analysts often need to inspect suspicious emails manually across
multiple tools. Important evidence is spread across:

- RFC 5322 headers
- MIME structure
- URLs, domains, and IP addresses
- SPF, DKIM, and DMARC results
- Received-server chains
- Attachment metadata
- Threat-intent analysis

Existing tools may provide isolated results, but an analyst still needs to
connect the evidence, understand provenance, and distinguish observed facts
from probabilistic conclusions.

Our MVP creates one investigation workflow for this process.

The backend is intentionally a modular monolith rather than microservices.
This reduces deployment and debugging complexity for an MVP while keeping
responsibilities separated internally.

Important backend boundaries:

- parser: reads and normalizes untrusted email content
- forensics: deterministic header and relay analysis
- ai: provider adapter and validated AI assessment
- email service: coordinates the pipeline
- persistence: PostgreSQL and test store implementations
- httpapi: transport, routing, and API error mapping

============================================================
6. DATA AND FORENSIC PROVENANCE
============================================================

The system distinguishes:

OBSERVED:
Directly present in the raw email, such as a header value or URL.

PARSED:
Normalized from observed data, such as a parsed address or relay structure.

INFERRED:
Derived by deterministic logic, such as relay ordering or an anomaly.

AI-ASSESSED:
Probabilistic output from Gemini, such as phishing intent.

This distinction prevents an AI conclusion from being presented as confirmed
ground truth.

AI confidence means confidence in the classification, not confidence in the
identity or physical location of an attacker.

============================================================
7. AI INTEGRATION
============================================================

The backend uses this stable interface:

type Analyzer interface {
    Assess(context.Context, Input) (domain.AIAssessment, error)
}

The adapter receives:

- sender and recipient metadata
- subject and date
- normalized plain-text body
- headers
- extracted indicators
- attachment names, types, sizes, and hashes
- case and analysis identifiers

The adapter does not receive attachment bytes. It does not execute content,
run scripts, or browse URLs.

Configuration is local runtime configuration:

GEMINI_API_KEY
GEMINI_MODEL
GEMINI_TIMEOUT

Example successful result:

{
  "status": "completed",
  "ai_assessment": {
    "status": "completed",
    "classification": "Phishing",
    "confidence": 0.9,
    "supporting_signals": [
      "Urgent account verification language",
      "Credential collection URL pattern"
    ],
    "evidence_references": [
      "message.subject",
      "plain_text_body",
      "indicators.urls"
    ],
    "provider": "google",
    "model": "gemini-2.5-flash"
  }
}

If Gemini fails, parsing and deterministic evidence remain available. The API
returns a partial result rather than hiding or fabricating evidence.

============================================================
9. SCALABILITY
============================================================

Current scale:

- A modular monolith is sufficient for the hackathon and early MVP.
- HTTP handlers are stateless apart from PostgreSQL-backed data.
- PostgreSQL can be scaled vertically and later read-replicated.
- Redis can cache repeated analyzer and enrichment results.
- External providers are isolated behind interfaces.
- The AI adapter can be replaced without changing the frontend contract.

How we scale later:

1. Move long-running analysis from synchronous request handling to a job queue.
2. Store analysis-stage progress in Redis/PostgreSQL.
3. Run multiple stateless Go API instances behind a load balancer.
4. Run analysis workers separately from API processes.
5. Cache repeated domain/IP/URL analysis.
6. Add PostgreSQL indexes and partitioning for large event and evidence tables.
7. Use object storage for large raw email artifacts while keeping hashes and
   metadata in PostgreSQL.
8. Add rate limits and provider quotas.
9. Add tracing, metrics, structured audit logs, and retry policies.

Why not microservices now:

Microservices would add network, deployment, and debugging overhead before the
MVP has enough traffic to justify it. Internal module boundaries preserve a
future extraction path without slowing the hackathon.

11. SECURITY QUESTIONS JUDGES MAY ASK
============================================================

Q: Do you execute attachments?
A: No. We only extract metadata and SHA-256 hashes.

Q: Do you browse links in the email?
A: No. URLs are extracted as evidence. Automatic retrieval is deliberately
disabled.

Q: Can prompt injection inside an email control the AI?
A: Email content is treated as untrusted data. The provider prompt instructs
the model not to follow instructions inside the email, and the adapter sends
normalized data rather than executing it.

Q: What happens if Gemini is unavailable?
A: The backend returns a structured partial or failed AI assessment while
preserving parsed and deterministic evidence.

Q: Are AI results treated as facts?
A: No. They are explicitly labeled AI-ASSESSED and include confidence and
evidence references.

Q: How are secrets handled?
A: API keys are loaded from environment variables and are not committed,
logged, or returned by the API.

============================================================
12. TECHNICAL QUESTIONS JUDGES MAY ASK
============================================================

Q: Why Go?
A: Go provides a small, fast, type-safe backend with simple deployment and
good support for concurrent analysis workers later.

Q: Why PostgreSQL?
A: The data is relational and evidence-linked: cases, emails, headers,
indicators, analysis results, and audit events benefit from transactions and
structured queries.

Q: Why is Redis present?
A: It is reserved for short-lived state, rate limits, and analyzer caching.
The MVP does not depend on it for core correctness.

Q: Why is the AI provider behind an interface?
A: It prevents the domain and API from being coupled to Gemini. Another model
or local classifier can be substituted later.

Q: Is the analysis deterministic?
A: Parsing, extraction, authentication interpretation, and relay processing
are deterministic. AI output is probabilistic and is labeled accordingly.

Q: How do you test it?
A: We use Go unit tests, HTTP tests, parser fixtures, provider test servers,
and React/Vitest tests. We also validate the live upload-to-analysis flow with
the local API.

Q: Why separate risk and confidence?
A: Risk describes threat severity. Confidence describes how strongly the
available evidence supports the conclusion. Combining them would be
misleading.

13. COMPETITIVE DIFFERENTIATION
============================================================

VirusTotal:

- Strong broad indicator and reputation aggregation.
- Our focus is a guided email-forensics workflow with preserved email
  provenance, relay reconstruction, and explainable AI intent.

ANY.RUN and sandbox platforms:

- Strong dynamic execution and malware sandboxing.
- Our platform is intentionally safer for initial email triage: it does not
  execute attachments or browse URLs automatically.
- We focus on headers, authentication, infrastructure evidence, and explainable
  case reconstruction.

Maltego:

- Strong general-purpose relationship and graph investigation.
- Our product starts with a specialized email evidence model and automatically
  turns one email into structured forensic entities and signals.

GreyNoise and reputation services:

- Strong network and IP intelligence.
- Our platform connects network indicators back to the original email evidence
  and AI-assessed intent rather than presenting isolated reputation results.

Traditional secure email gateways:

- Strong prevention and mail-flow controls.
- Our platform is an analyst-facing forensic investigation and explanation
  tool for suspicious artifacts, including emails already received or
  collected as evidence.

Our core differentiation:

1. Evidence-first workflow: preserve the artifact and trace conclusions to it.
2. Email-specific forensic context: headers, MIME, relays, authentication,
   indicators, and AI intent in one flow.
3. Safe-by-default analysis: no attachment execution and no automatic URL
   retrieval.
4. Explicit epistemic labeling: observed, parsed, inferred, and AI-assessed
   information are not mixed.
5. Explainable AI output: classification, confidence, signals, and evidence
   references are returned together.
6. Modular provider design: Gemini can be replaced without redesigning the
   product.

We should not claim that the platform replaces VirusTotal, sandboxing, or
enterprise secure email gateways. It is an MVP investigation and triage layer
that combines their relevant ideas into a focused, explainable email-forensics
workflow.

============================================================
15. FINAL POSITIONING
============================================================

SIH26106 is not trying to be a complete replacement for every security
platform. It is a focused, safe, and explainable forensic email investigation
MVP. Its value is bringing raw email evidence, deterministic protocol signals,
infrastructure clues, and AI-assisted intent assessment into one traceable
workflow.
